## 2. CONSTATS CRITIQUES 🔴

### C1 — Bloc `/api/timetables*` 100 % non authentifié, exécuté avec la clé service_role
**Fichiers :** `backend/api/src/index.js:112-115`, `backend/api/src/routes/timetables.js` (tout le fichier) — **vérifié manuellement** ✅

Le routeur est monté **sans aucun guard** : pas de JWT, pas de rôle, pas de rate limit, pas de validation d'entrées. Le client Supabase utilisé est le **service_role** (contourne toute RLS).

```js
// index.js:112 — monté brut, avant même le bloc admin
app.all("/api/timetables", timetables);
```

```js
// timetables.js:11 — client service_role
const svc = createClient(SUPABASE_URL, SERVICE_KEY, ...);
// timetables.js:20-25 — filtre schoolId OPTIONNEL : sans lui, TOUTES les écoles
let query = svc.from("timetables");
if (schoolId) query = query.eq("school_id", schoolId);
```

**Attacker scenario (réel) :**
```bash
# Lire les emplois du temps de TOUTES les écoles :
curl https://<api>/api/timetables
# Modifier un EDT de n'importe quelle école :
curl -X PATCH https://<api>/api/timetables/12 -H "Content-Type: application/json" -d '{"name":"hacké"}'
```

**Bugs connexes dans le même fichier (confirmés) :**
- `timetables.js:36` — `created_by: req.user.id` : aucun middleware ne définit `req.user` → **tout POST crashe** (500 systématique) ;
- `timetables.js:24,38,59,66,85` — `serverError(res, error.message)` : **messages Postgres bruts renvoyés au client** (noms de tables/colonnes → reconnaissance) ;
- routes `/publish` et `/courses` codées dans le handler (`timetables.js:62,68`) mais **non montées** dans `index.js` → 404 en production ;
- aucune validation (`schoolId`, `classId`, `day`, heures libres) ;
- `export-pdf` est un stub (`timetables.js:88-91`).

**Correction :** brancher `requireDirecteur` (ou rôle école approprié) + `school_is_writable`, prendre `school_id` **uniquement** du profil de l'appelant (jamais du query/body), valider toutes les entrées, renvoyer des erreurs génériques (log côté serveur), ajouter un rate limit. Ou, si le module n'est pas encore utilisé en production : désactiver les routes complètement.

### C2 — Violation des règles des Hooks → crash possible de la page Messages
**Fichier :** `frontend/src/pages/app/MessagesPage.tsx:35-64` — **vérifié manuellement** ✅

Le `return` paywall est placé **avant** les appels `useAsync` (L56-58) et `useState` (L59-64) :

```tsx
if (!hasMessaging) {
  return (… carté bloqué …);   // L35
}
// … PUIS :
const convs = useAsync(...);   // L56
const [tab, setTab] = useState(…); // L59
```

Scénario : le plan de l'école passe Pro → Découverte pendant que l'utilisateur est sur la page (changement d'abonnement, refresh du cache) → React lève « Rendered fewer hooks » → **crash de la page**.

**Correction :** extraire le paywall dans un composant dédié (`<MessagingPaywall/>`) et faire le `if(hasMessaging)` APRÈS tous les hooks (ou dans un composant parent conditionnel).

### C3 — (à vérifier selon la configuration du projet) Truncate possible sur les tables à « zero policy »
**Fichiers :** `20260101000001_foundation.sql:429-439` (`audit_log`), `00003:162-164` (`contact_messages`), `00010` (`messages`, `conversations`, `announcements`)

RLS empêche les DML au niveau ligne mais **ne bloque PAS `TRUNCATE`**. Supabase a historiquement accordé `ALL` aux rôles `anon, authenticated` sur les nouvelles tables ; si votre projet doit ce comportement par défaut, un simple compte élève connecté peut exécuter (via PostgREST RPC ou toute surface SQL) et vider `audit_log` / `students` (cascade).

**Vérification à faire (1 requête) :**
```sql
select table_name, privilege_type from information_schema.role_table_grants
where grantee in ('anon','authenticated') and privilege_type in ('TRUNCATE');
```
Si des `TRUNCATE` apparaissent → **CRITIQUE confirmé**. Sinon le constat est déjà clos.

**Correction préventive (1 migration) :**
```sql
revoke truncate on all tables in schema public from anon, authenticated;
alter default privileges in schema public revoke truncate on tables from anon, authenticated;
```

## 3. CONSTATS HAUT 🟠

### H1 — Policies SQL tautologiques → écriture croisée inter-écoles possible
**Fichiers :** `20260101000006_structure.sql:684-701` (`class_subjects`), `:715-723` (`teaching_assignments`) — **vérifié manuellement** ✅

```sql
-- 00006:689 : le « school_id » NON qualifié à droite se résout sur c.school_id
-- (la colonne du FROM intérieur) → c.school_id = c.school_id → toujours vrai.
and exists (select 1 from public.class_rooms c
            where c.id = class_id and c.school_id = school_id)
```

La migration 00015 a reconnu **exactement ce bug** et l'a corrigé pour `grades/payments/report_metas` — mais a **oublié** ces 3 policies. Conséquence : un directeur de l'école A peut rattacher une **classe de l'école B** à sa matière (ou un enseignant de B à sa classe), ce qui pollue le référentiel et fait fuiter des noms d'enseignants/classe de B dans la vue d'A (`assignment_conflicts` jointe par `id`).

**Correction :** qualifier, comme en 00015 : `c.school_id = class_subjects.school_id`, `t.school_id = teaching_assignments.school_id`, pour INSERT et UPDATE.

### H2 — Inscription élève (00028) sans contrôle de limite ni de blocage → inflation d'effectif
**Fichier :** `20260101000028_child_code_immediate.sql:36-69, 84-92`

Le 00028 crée l'élève **dès l'inscription** (avant tout contrôle de `school_is_writable` et de la limite d'élèves) : quiconque connaît le matricule d'école peut faire exploser l'effectif EN_ATTENTE jusqu'à bloquer les approbations (`limit_reached` compte *tous* les élèves) et alimenter une école expirée/bloquée.

**Correction :** vérifier `school_is_writable` + la limite (>verrou `pg_advisory_xact_lock` comme dans `decide_registration_requests`) **avant** l'insert de l'élève.

### H3 — Fusion d'identité « par homonymie » (00028) — le plus dangereux métier de la base
**Fichier :** `20260101000028_child_code_immediate.sql:196-204` (rattachement), `:249-254` (suppression au refus)

À l'approbation d'une demande, la fonction retrouve l'élève par `prénom + nom + date de naissance` :
- **Scénario 1 (usurpation)** : un attaquant s'inscrît avec le nom + date de naissance d'un élève réel de la classe cible → à l'approbation (le directeur croit valider une demande normale), le compte attaquant est lié à l'élève réel → **lecture des notes/paiements/bulletins de l'enfant** via les policies rôle élève, et réécriture de la classe de l'élève réel.
- **Scénario 2 (perte de données)** : un refus → `delete from students where prénom+nom+date` → **suppression de l'élève légitime** et cascade de ses notes/paiements/messagerie.

**Correction :** retrouver l'élève via `profiles.student_id` de `v_req.user_id` (déjà posé à l'inscription) — jamais par homonymie. Au refus **jamais** de `delete by name`.

### H4 — CORS « fail-open » quand `NODE_ENV` n'est pas défini
**Fichier :** `backend/api/src/lib/http.js:20-24` — **vérifié manuellement** ✅

```js
if (!FRONTEND_ORIGIN) return process.env.NODE_ENV !== "production";
```
Le service est démarré par `node src/index.js` (Render ne définit pas toujours `NODE_ENV` à Express) et l'absence de `FRONTEND_ORIGIN` déclenche un warning au démarrage mais ** laisse CORS ouvert à toutes les origines**. Pas de `credentials` (impact limité), mais à fermer.

**Correction :** fail-closed → `if (!FRONTEND_ORIGIN) return false;`.

### H5 — Suppression d'école non transactionnelle (perte de données possible)
**Fichier :** `backend/api/src/routes/adminSchools.js:238-261`

Les élèves sont supprimés **avant** l'école ; si la suppression de l'école échoue ensuite, les élèves sont perdus alors que l'école existe encore. De plus, la suppression des comptes Auth est un N+1 séquentiel (très lent, partiel en cas d'échec).

**Correction :** déplacer toute la purge dans une RPC `security definer` transactionnelle (comme le modèle `finish_director_registration`).

### H6 — Module `timetableService` frontend : update/delete sans aucun scope école
**Fichier :** `frontend/src/services/timetableService.ts:219-281`

`updateCourse`, `publishTimetable`, `unpublishTimetable`, `deleteCourse(timetableId)`, `deleteTimetable(timetableId)` ne filtrent **ni `school_id` ni ownership**, contrairement à tous les autres services. Ils s'en remettent entièrement aux policies RLS 00034 — qui elles-mêmes ne vérifient pas l'appartenance de `subject_id`/`teacher_id`/`class_id` à l'école (cf. M5).

**Correction :** ajouter `.eq("school_id", schoolId)` (comme le reste du service layer) + joindre `timetableId` aux sous-entités, et couvrir `timetable_courses` par des policies same-school.

### H7 — Cache global : 18 tables entières téléchargées dans le navigateur
**Fichier :** `frontend/src/services/db.ts:354-490` (`fetchAllRows` / `hydrateAll`)

À chaque login/session, l'app télécharge **toutes** les lignes (jauge 100 000) de 18 tables — les conversations, notes, paiements, téléphones de parents de tout l'établissement, y compris pour un simple compte élève. Le cache PII est gardé pendant toutes la session, sans purge.

**Correction :** hydrater seulement les entités utilisées (les fichiers indiquent `hydrate(x)` granulaire), supprimer `hydrateAll`, purger au `visibilitychange`/logout inactif. Corrige aussi la sévérité de tout futur affaiblissement RLS (aach : moins de données exposées = moins d'amplication).

### H8 — Regex téléphone du Sénégal : les numéros `75` sont refusés
**Fichier :** `frontend/src/utils/format.ts:69` — **vérifié manuellement** ✅

```ts
/^(\+221)?\s?7[0678]\s?\d{3}\s?\d{2}\s?\d{2}$/ // 70/76/77/78 — 75 manquant
```
Tout parent/enseignant/élève avec un numéro `75 123 45 67` est rejeté dans **tous** les formulaires. Numéros réels du Sénégal (Free/Promobile) exclus de la plateforme.

**Correction :** `7[(7078)]` → couvrir 70/75/76/77/78.

### H9 — Secrets réels présents localement dans le dossier synchronisé (OneDrive)
**Fichiers :** `backend/api/.env.local:6` (`SUPABASE_SERVICE_ROLE_KEY=sb_secret_…` réel et actif), `frontend/.env.local:1` (`SCOLIA_WEBHOOK_SECRET=…`)

Ce serait aussi bien dans le dossier **frontend** (retiré du git et absent de l'historique, vérifié sur tout le repo). Mais : réplication le cloud Microsoft OneDrive + risque d'un `git add -f` accidentel. Et le secret **HMAC du webhook** est mal placé dans le dossier frontend (c'est un secret **serveur**).

**Correction :** sortir `SCOLIA_WEBHOOK_SECRET` du frontend (rester sur Render uniquement), envisager une rotation des clés si le poste est partagé, et ajouter un hook pre-commit anti `sb_secret`.

## 7. POINTS FORTS À PRÉSERVÉE ✔

- **Backend** : rôles lus en base (jamais du JWT client), JWT vérifié à chaque route privilégiée, `rate_limit` SQL atomique fail-closed et IP = dernier XFF (non falsifiable), validations solides (`validate.js`), erreurs génériques avec pas de stack au client, séparations admin/school mutuelles (guard croisé).
- **Base** : deny-by-default, aucune `USING(true)` côté écriture client, fonctions definer durcies (`search_path` + revoke/grant), rôle en `app_metadata` non modifiable client + fallback `profiles` non-grantée en UPDATE, aucun hash de mot de passe en base publique, migrations de durcissement systématiques (00011, 00015, 00021, 00029…).
